## 0. 这一阶段解决什么问题（组会开场）

阶段 3 的软件有两个"能用但不专业"的地方：

1. **只认 .npy 一种格式** —— 真实数据可能是 csv/txt/mat，接口还没定，来了就得改代码。
2. **读文件在界面线程里干** —— 文件一大，窗口就转圈、点不动，像死机。

阶段 4 把这两件补齐：**数据入口支持多种格式 + 读文件丢到后台线程，界面不卡**。

## 1. 数据入口升级：按后缀分派（K4.1 / 4.2 / 4.3 / 4.9）

### 一句话原理

`load_rd()` 现在会看文件的**后缀名**，自动选对应的读取函数：

```
xxx.npy  → _load_npy()  → np.load()
xxx.csv  → _load_text() → np.loadtxt(delimiter=",")
xxx.txt  → _load_text() → np.loadtxt(delimiter=",")
xxx.mat  → _load_mat()  → scipy.io.loadmat()   （用到才装 scipy）
```

### 新词拆根

| 词 | 拆开 | 字面意思 |
|---|---|---|
| `suffix` | suf + fix | 后缀（跟在后面的部分），`.npy` 就是后缀 |
| `loadtxt` | load + txt | 读文本 |
| `delimiter` | de + limit + er | 分隔符（用来切分每列的东西），csv 里是逗号 |
| `loadmat` | load + mat | 读 MATLAB 的 .mat 文件 |
| `scipy` | scientific + python | 科学计算的 Python 库 |
| `ndim` | n + dimension | 第几维（2 维矩阵 ndim=2） |

### 三个关键设计（组会可讲）

**① 为什么"用到才 import scipy"？**
scipy 只在读 .mat 时才需要。把它写在 `_load_mat()` 函数里面，而不是文件顶部——这样平时读 npy/csv 根本不需要 scipy。而且没装时给一句人话安装提示（`RuntimeError`），不是甩一个 `ModuleNotFoundError` 让界面崩掉。这叫**按需依赖 / 优雅降级**。

**② `.mat` 读出来是字典，不是数组**
MATLAB 一个文件能存多个变量，所以 `loadmat()` 返回 `{"变量名": 数组, "__header__": ...}`。我们跳过 `__` 开头的元数据，取真正的变量。但**变量名是什么要问数据同学**（接口清单的隐藏坑）。

**③ 读完必做自检**
```python
if rd.ndim != 2: raise ValueError(...)
print(f"shape=..., 范围 ... dB")
```
这是接口对不上时**最快的发现手段**：维度不对、量级不对，终端一眼看见。组会讲"我用 assert + 打印把接口风险前置暴露"。

### 单位转换 `to_db()`（对应接口清单第 3 问）

接口还没回：数据是 dB、线性功率、还是复数 I/Q？先写好转换，默认按 dB：

| 单位 | 转成 dB 的公式 | 为什么 |
|---|---|---|
| `db` | 不用转 | 当前假设 |
| `power`（线性功率） | `10*log10(p + 1e-12)` | dB 定义；`+1e-12` 防止 log(0) 报错 |
| `iq`（复数） | `10*log10(|iq|² + 1e-12)` | 功率 = 幅度²，再取 dB |

接口定了，只改 `DEFAULT_UNIT` 一个常量。

## 2. 防卡死：QThread 工作线程（K4.4 / 4.5 / 4.6 / 4.7）

### 先搞懂"为什么会卡"

界面程序有一个**主线程**，它一边跑事件循环（响应点击），一边画界面。如果点按钮后，读一个 500MB 的文件在主线程里干 3 秒——这 3 秒里主线程腾不出手响应任何点击，窗口就"假死"。

**脚本不会有这问题**：脚本从头跑到尾，本来就没"响应点击"这回事（阶段 1 顺序执行，K2.8）。

### 新词拆根

| 词 | 拆开 | 字面意思 |
|---|---|---|
| `QThread` | Qt + thread | Qt 的线程类；thread=线（一条独立的执行线索） |
| `Signal` | 信号 | 线程之间传消息的"信使" |
| `emit` | 发出 | 发信号（emit 一个信号 = 把消息寄出去） |
| `worker` | 干活的人 | 在后台干活的对象 |
| `finished` | 完成 | 线程干完活自动发出的信号 |

### 核心机制：三信号 + 一个规矩

```
主线程（界面）                  工作线程 LoadWorker
    │                                  │
    │ on_open_file():                  │
    │   worker.start() ──────────────→ │ run(): 读文件（耗时）
    │                                  │
    │   ←────── loaded(数组) ───────── │ 读成功：把数组寄回来
    │ _on_loaded(): 画图                │
    │   ←────── failed(文字) ───────── │ 读失败：把错误寄回来
    │ _on_failed(): 提示                │
    │   ←────── finished ───────────── │ 干完了（不管成败）
    │ _on_finished(): 恢复按钮          │
```

**一个铁规矩**（组会必答）：

> **工作线程绝对不能碰界面控件。** 想在后台线程里直接 `self.label.setText(...)`？Qt 会报错甚至崩溃——界面只能在主线程改。所以后台只负责"读数据"，读完用 `Signal` 把数据寄回主线程，由主线程的槽函数 `_on_loaded()` 去画图、改标签。

这就是 K4.6「跨线程用信号传数据」的实质。**QThread 不是让读文件变快，是让界面在读的时候还能响应。**

### 防重复点击（K4.7）

`on_open_file()` 一进来 `self.open_btn.setEnabled(False)`，读完在 `_on_finished()` 里恢复。不这么做，用户连点三下就开三个线程同时读，图乱跳还浪费资源。

## 3. 默认数据兜底（K4.8，修阶段 3 的技术债）

## 4. 三种程序结构对比（串起阶段 1/2/3/4）

| 阶段 | 程序类型 | 耗时读文件在哪 | 特点 |
|---|---|---|---|
| 1 | 脚本 | 主线程（顺序执行） | 跑完就退，没有"响应"问题 |

## 6. 亲手参与闭环：卡 vs 不卡的对照实验（2026-11-25 补）

> 这条是阶段 4 台账里写明的「负责人必须亲手做一次」的验收。用程序代替肉眼，留下可复现的证据。

### 6.1 为什么需要"大文件"

正常的 `fake_rd.npy`（128×64）一眨眼就读完，肉眼看不出卡不卡。所以先造一个**读起来明显慢**的文件：

```bash
.venv\Scripts\python.exe 04_thread\make_slow_rd.py
```

它造一个 4000×4000 的 `.csv`（约 109MB）。选 csv 不选 npy 的原因：**npy 是二进制读得快，csv 是文本要一行行解析**，实测读取约 2.8 秒，正好够肉眼分辨。（脚本末尾会实测并打印耗时；想更卡就把里面的 `N` 调大。）

### 6.2 心跳检测原理（这是本实验的核心概念）

怎么"测量"界面卡不卡？用 **QTimer 心跳**：

- 让计时器每 100ms 往主线程事件队列投一次"心跳"，记录它实际到达的时间。
- **主线程被占住时**（阶段 3 同步读文件），事件队列没法处理心跳 → 心跳迟到 → 延迟≈被卡时长。
- **主线程空闲时**（阶段 4 后台读文件），心跳准时到达 → 延迟很小。

类比：主线程是前台服务员，心跳是"你还活着吗"的电话。服务员被拖去搬 3 秒箱子（读文件），电话就 3 秒没人接；派后厨去搬（工作线程），服务员继续接电话。

### 6.3 运行与实测结果

```bash
.venv\Scripts\python.exe 04_thread\verify_no_freeze.py
```

> ⚠️ **踩坑记录（2026-11-25 现场）**：曾给命令 `QT_QPA_PLATFORM=offscreen python ...`，Windows CMD 报「'QT_QPA_PLATFORM' 不是内部或外部命令」——那是 Linux/Mac 写法。CMD 里临时设环境变量要用 `set QT_QPA_PLATFORM=offscreen`，PowerShell 用 `$env:QT_QPA_PLATFORM="offscreen"`。**现在脚本内部已经设好（在 import PySide6 之前），你直接跑上面那行就行，不用加任何前缀。**
> 这正是知识点地图 K0.10「三层定位法」之外的第四层坑：**命令语法本身跨平台不通**。记住规律：`VAR=value cmd`（Linux）vs `set VAR=value && cmd`（CMD）vs `$env:VAR="value"; cmd`（PowerShell）。

本机实测（2026-11-25，文件 `slow_rd.csv` 109MB）：

| 指标 | 阶段 3（主线程直接读） | 阶段 4（QThread 后台读） |
|---|---|---|
| 读文件耗时 | 2.79 s | 2.88 s |
| 主线程心跳最大延迟 | **2756 ms** | **22 ms** |
| 人话 | 界面假死近 3 秒 | 界面全程能响应 |

### 6.4 这组数据怎么讲（组会直接用）

> "我做了个对照实验来证明 QThread 的作用：同一个 109MB 文件，读文件耗时两边几乎一样，2.79 秒对 2.88 秒——**所以多线程不是让读文件变快**。但我用 QTimer 心跳测主线程响应，阶段 3 心跳迟到 2756 毫秒，就是界面卡死近 3 秒；阶段 4 只迟到 22 毫秒，界面全程能点。这就印证了：QThread 的价值是**把耗时活挪出主线程，让界面在读的时候还能响应**。"

一句话记忆：**读多快是磁盘和解析决定的，卡不卡是"谁在读"决定的。**

## 7. 认知减压：线程知识分两层（2026-11-25 补）

> 负责人反馈「操作系统我还没学」，担心线程搞不懂。澄清：**会用 ≠ 学完背后的整门课**。

### 7.1 两层划分

| 层 | 内容 | 现在要做吗 |
|---|---|---|
| **会用层**（绿色） | ① 一个程序=一个进程，可含多条线程 ② 主线程管界面、工作线程读文件 ③ 共享内存不用拷贝 ④ 工作线程用 Signal 送回主线程 | ✅ **现在必须懂——前面第 1~6 节已全部覆盖，且负责人已用自己的话讲过** |
| **原理层**（灰色） | CPU 调度算法 / 竞态与锁 / GIL / 死锁 / 线程池 | ❌ 大三操作系统课再学，现在完全不用碰 |

### 7.2 四个"原理层"名词（只求眼熟，不求懂）

| 名词 | 一句话 | 现在 |
|---|---|---|
| CPU 调度 | 多线程抢 CPU，系统决定谁先用 | 不用 |
| 竞态与锁 | 两个线程同时改一个数据会乱，要上锁 | 不用（Qt 用 Signal 帮你绕开了） |
| GIL | Python 限制：同时刻只有一个线程跑 Python 代码 | 不用（读文件是 C 层干的，不受影响） |
| 死锁 | 两线程互相等对方放手 | 不用 |

### 7.3 关键认知

> 编程知识是**分层**的。开车不用懂发动机原理，照样能考驾照、能上路。
> 现在是在**学开车**（用 QThread 做软件），不是**学造发动机**（操作系统原理）。
> 等大三开了操作系统课，带着"项目里真用过线程"的经验去听，反而学得更轻松——脑子里挂着真实案例。

**老师不会问一个大二学生"讲讲 CPU 调度算法"**——那不是本项目考核范围，是期末卷子上的题。组会问的就是会用层，已经够了。

## 8. 交付前体检发现的真 bug（2026-11-26）

> 这一节记录一次**真实的查错→定位→修复→验证**闭环，组会讲出来是加分项：
> 它说明我做了交付前的代码体检，不是"写完就交"。

**现象**：界面能换图（所以肉眼验收"正常"），但文件名标签一直停在"还没有选择文件"、状态栏停在"正在读取（后台）…"，不更新。

**定位**：用自动化测试模拟"选文件"，抓到 stderr 里的报错：
```
File "04_thread/rd_viewer_threaded.py", line 150, in _on_loaded
    self.file_label.setText(self.worker.path.name)
AttributeError: 'str' object has no attribute 'name'
```
根因：`QFileDialog.getOpenFileName()` 返回的是**字符串**，`LoadWorker.__init__` 里 `self.path = path` 直接存了字符串；字符串没有 `.name` 属性。对比阶段 2、3 都正确写了 `Path(path).name`——阶段 4 拆成 worker 类时漏了这层转换。

**为什么肉眼没发现**：`_draw(rd)` 在报错那句**之前**执行，所以图照常刷新；异常发生在槽函数里、`--windowed` 又把 stderr 吞掉，界面上看不出异常。这正是"能跑 ≠ 没 bug"的典型——**图形界面软件必须盯状态栏/标签这些反馈细节，不能只看主图**。

**修复**：`LoadWorker.__init__` 里改成 `self.path = Path(path)`，一处转换，两个用处（`.name` 取文件名、传给 `load_rd()` 也接受 Path）。

**验证**：重跑自动化测试，断言标签 == `fake_rd_v2.npy`、状态栏含"已显示"，全部通过，stderr 干净。

**教训（组会可讲）**：把数据从主线程交给另一个类时，**类型契约要显式**——对话框给的是 str，界面显示要的是 Path 的 `.name`，中间必须转。这类 bug 编译器不会报（Python 是动态类型），只能靠测试覆盖"点按钮之后的每一步反馈"。
